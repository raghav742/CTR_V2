## D1 — Develop on V1, switch hardware via profiles
**Decision:** All hardware differences live in one profile file; V1 and V2 are separate build environments.
**Why:** Firmware is developed on the unchanged V1 robot; moving to V2 should mean changing a profile, not code.
**Alternatives:** Separate branches per robot (rejected: changes would have to be made twice).

## D2 — V1 encoder: pin 49 is the encoder supply, no red LED
**Decision:** On V1, pin 49 is driven HIGH permanently as the encoder's "+" supply. Status colours use green, blue and cyan only. The button is read active HIGH without the internal pull-up.
**Why:** Measured 2026-10-28: driving pin 49 LOW switches off all LEDs and the button; red never lights. The "+" and red wires are swapped between PCB connector P1 and the encoder. No hardware changes are allowed on V1.
**V2:** Swap the two wires back; full RGB becomes available (profile setting `LED_HAS_RED`).

## D3 — Step pulses from one Timer1 interrupt, 20 kHz
**Decision:** A single Timer1 interrupt at 20 kHz generates STEP pulses for all six axes using a 16-bit phase accumulator per axis. Ramps are calculated in the main loop (every 1 ms) and passed to the interrupt as a rate. Microstepping: 8 (translation), 16 (rotation), with driver interpolation to 256.
**Why:** V1 generated pulses in blocking loops, freezing inputs and safety during motion. One timer for all axes keeps CPU use predictable; the accumulator gives each axis an independent speed. At 8 microsteps, 20 mm/s = 16,000 steps/s, under the 20,000 steps/s limit.
**Measured (simulation):** worst case (all axes at max speed) 45 % CPU in the interrupt.
**Alternatives:** One hardware timer per axis (the Mega has only 4 usable 16-bit timers); AccelStepper/FastAccelStepper (blocking-free but pin restrictions on AVR; V1 step pins don't fit).

## D4 — Translation axes use SpreadCycle
**Decision:** Translation drivers run in SpreadCycle at all speeds. Rotation stays in StealthChop (quiet). Settings in `motion_config.h` (`TRA_CHOPPER`, `ROT_CHOPPER`).
**Why:** Measured 2026-10-28. StealthChop on translation loses steps at 10, 15 and 20 mm/s (T1) and also at 5 mm/s (T3, about 5 mm lost over one cycle). Hybrid mode with a 5 mm/s switch-over therefore still slipped on slow moves. In SpreadCycle, T3 repeatability against its home switch: reference -54.65 mm; after fast (20 mm/s) cycles -54.67, -54.67; slow (3 mm/s) -54.57; i.e. within 0.1 mm, no steps lost. StealthChop has less torque under load; the lead-screw nut plus tube friction needs SpreadCycle.
**Cost:** Translation motors are slightly more audible at low speed.
**Alternatives:** Hybrid with a lower switch-over (not tested; StealthChop already slipped at 5 mm/s), higher current (already 1.9 A of the 2 A rating).

## D5 — Hardware watchdog in interrupt-then-reset mode
**Decision:** The ATmega2560 watchdog runs with a 1 s timeout in interrupt + reset mode. The main loop feeds it every pass. On the first timeout the watchdog interrupt switches off the step interrupt (no more step pulses) and marks the cause in RAM that survives a reset; one second later the board resets and reports "reset_cause=watchdog".
**Why:** A frozen program must never leave motors moving. Stopping the pulses in the interrupt works even if the board then fails to restart (older Mega bootloaders can hang after a watchdog reset).
**Alternatives:** Plain reset mode (no chance to stop pulses first; cause not reportable on bootloaders that clear MCUSR); no watchdog (V1).

## D6 — One text protocol for humans and programs
**Decision:** Plain-text lines with fixed prefixes (`OK`, `ERR`, `EV`, `ST`), `key=value` fields, optional request ids (`#<n>`), 250000 baud, 256-byte send buffer. The status stream skips a line rather than wait. Versioned with `PROTO_VERSION`; documented in `docs/protocol.md`.
**Why:** The same commands work in the Serial Monitor and from the laptop program, so everything the program does can be tried by hand. Ids let a program match replies while events and stream lines arrive in between. `info` makes the laptop program configure itself from the robot, so it works on V1 and V2 unchanged. Never waiting for USB keeps the safety loop fast.
**Alternatives:** Binary protocol (smaller, but unreadable when debugging and gains little at 250000 baud); JSON (readable, but large lines and slow to build on an 8-bit CPU).

## D7 — Driver health check once per second, blocking reads accepted
**Decision:** The safety manager checks one TMC2209 per second (round-robin, each driver every 6 s) using the TMCStepper library's blocking reads. Setting `DRV_CHECK_MS` in `motion_config.h`.
**Why:** Measured 2026-10-28: one check (alive + temperature) blocks the main loop for ~9 ms because TMCStepper waits inside each UART read. At the original 200 ms interval this happened 5 times a second. A 9 ms worst-case delay in noticing a limit switch is acceptable for the prototype (stop reaction measured 10.2 ms including it); checking less often makes it rare. The TMC2209 also protects itself (thermal shutdown in hardware).
**Cost:** Over-temperature or a lost driver is reported up to 6 s later; the 9 ms pause still occurs once a second.
**Alternatives:** Own non-blocking UART read (send request, collect reply over later loop passes; no pause at all, ~1 h work; revisit if switch reaction or display smoothness needs it); one read per check (halves the pause).

## D8 — Homing: fast approach together, slow approach per carriage
**Decision (v2.3.3):** All carriages move backward together in one coordinated move at 15 mm/s (same speed, so the gaps between them stay the same). When one reaches its switch the whole move stops and the others continue together. Then each carriage, back carriage first, refines its zero alone: forward until the switch releases + 2 mm, backward at 5 mm/s, zero where the switch is seen pressed (after the 5 ms debounce), forward until it releases + 1 mm. Homed axes have a soft minimum of 1.0 mm.
**Why:** (1) The tubes: a carriage may not get further ahead of the one behind it than at home, or the tube between them hangs unsupported and buckles (Raghav, 2026-10-30). Moving together keeps every gap constant; homing one carriage at a time (v2.1) left long unsupported spans. (2) Time: one fast trip for all three instead of three. (3) The switch ambiguity (switches 38/40 are pressed by the carriage's own block **or** by the carriage behind) does not cause a wrong zero: at equal speed two carriages can only close in once the one behind has stopped at its block, and because there is a gap between all carriages at home, the one in front then reaches its own block first. If a switch was pressed by the carriage behind at the start, that carriage does its own fast approach in the slow phase. (4) Only the slow approach sets the zero, so the fast one can be quick; robot repeatability with the slow approach was within 0.1 mm.
**History:** v2.1 one carriage at a time, slow only (accurate, slow, long unsupported spans); v2.3.1 one at a time with two speeds.
**Alternatives:** StallGuard sensorless homing (no switch, less repeatable, needs tuning).

## D9 — Travel limits from measured gaps, checked at the start of every move
**Decision:** `calib` measures the far end of the front carriage and, for each pair of carriages, the gap they have when both are homed (drive the back one onto the front one until the switch on the front one's back clicks; gap = back position − front position). Rules between each carriage and the one behind it: **span** front ≤ back + 1 mm (never further apart than at home, so no tube hangs unsupported; needs homing only), **contact** back ≤ front + gap − 2 mm; and the front carriage ≤ far end − 2 mm. T3 keeps 50 mm extra from its contact limit (`CARRIAGE_EXTRA_MARGIN_MM`, hardware profile): at its full measured range (~615 mm) it disturbed the front of the robot. The span rule is applied to homing and calib only (v2.5.1): those sequences make long moves and keep the carriages together by design, while manual moves are short and must be able to move each tube individually (`SPAN_RULE_FOR_MOVES`, default false). `calib` itself follows the span rule: all three forward together to the far switch, T2 + T3 together onto T1, T3 alone onto T2, all back together. Checked once, before a move starts, on the end positions. A move is refused if a neighbouring carriage is busy in a different move. Until calibrated (and while not all carriages are homed) translation moves stay limited to 50 mm each.
**Why:** The switches on the carriages are only a backup: when the front carriage rests on its own block, its switch is already pressed and a carriage touching it gives no new edge. Software limits stop a dangerous move before it starts instead of as an emergency stop. Coordinated moves are proportional, so every gap changes linearly from start to end; if it is allowed at both ends it is allowed throughout. A carriage in another move has an end position the check cannot know, so that case is refused ("combine them in one mv").
**Known values and plausibility (v2.3.6):** The measured values are also stored in the hardware profile and loaded at startup, so the limits work after `home` alone. `calib` rejects any value more than 5 mm from the profile value and always ends with a fresh `home`. Reason: the V1 mechanics slip (T1 lost up to ~20 mm in long fast moves), so a single calib run cannot be trusted blindly; a rejected run changes nothing. For V2: run calib once, copy the values into `hw_profile_v2.h`, and the same protection applies.
**Alternatives:** Live gap monitoring during motion (needed only for independent simultaneous moves, which are refused); fixed numbers measured with a ruler (less precise, must be edited in code after any mechanical change and for V2).

## D10 — Rotation zero by hand + parking, settings in EEPROM
**Decision:** Rotation axes get their zero by hand (`zero`), and keep it across power cycles by parking: `park` turns them to a full turn of their zero and stores a "parked" flag in EEPROM; at startup the flag restores the zeros. The EEPROM also keeps the last accepted calib result. Data is protected by magic number, version and checksum, and calib values are only used if they are within 5 mm of the hardware profile values.
**Why:** No rotation sensor on V1 (and none planned for V2). A switched-off stepper keeps its position (it may settle to the nearest full step, at most 0.9 deg), so a robot parked before power-off starts with known angles. Parking to the *nearest* full turn takes the shortest way. Writing only on calib, park and the first rotation move after a park keeps EEPROM wear negligible.
**Alternatives:** Rotation index sensor (hall sensor + magnet per tube; precise, needs hardware, possible V2 extra); storing the live position continuously (wears out the EEPROM); StallGuard against a mechanical stop (tubes rotate freely, no stop).

## D11 — OLED updated in small pieces, text drawn byte-wise
**Decision:** The OLED frame (1 KB) is sent in 16-byte I2C transfers, one per loop pass. Frequently redrawn content (text, bars) is written directly into the frame buffer byte by byte (`fastgfx`); screens are drawn in parts over several loop passes. Adafruit GFX is kept for drawing and for one-off graphics.
**Why:** The safety loop must never pause long: a full Adafruit refresh blocked it for ~21 ms at rest and up to ~69 ms under full motion load (measured in simulation), longer than the 9 ms driver check we already accepted reluctantly (D7). With these three measures the longest loop pass with the display running is 2.6 ms under full load.
**Alternatives:** Adafruit `display()` at a low refresh rate (still 25+ ms pauses); a display with its own controller/serial protocol (V2 TFT will need the same care: SPI is faster, but a 320x240 frame is much larger, so partial updates will be essential); updating only changed areas (more complex; not needed at this frame rate).

## D12 — Demo poses as outer position plus tube extensions
**Decision:** Demo steps describe the tubes as T1 position (fraction of its stroke) plus the extension of each inner tube beyond the one around it (fraction of the usable gap), and rotations in degrees. The sequencer converts this to absolute positions with the measured geometry (`limits::geometry`) and moves all axes in one coordinated move per step.
**Why:** With this description every value combination satisfies both the span rule (tube supported) and the contact limit, so a demo cannot be written that crashes or buckles the tubes. It matches how concentric tube robots are described (tube translation relative to the outer tube), and the same demo runs on V2 with its own stroke and gaps. Coordinated moves keep the relations linear between poses, so checking the poses is enough.
**Alternatives:** absolute mm per carriage (simple, but easy to write unsafe or V1-specific demos); a scripting language over serial (later, from the laptop control centre in phase 4).
